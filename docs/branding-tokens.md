# Re-branding: colour & font tokens

**On first run, `bin/setup` asks for it directly** — client/site name, tagline, business contact
details, primary brand colour, accent colour, heading font, body font — and applies everything
automatically before seeding content.

**Nothing here is a blocker.** Every single question has a bracketed default, filled in just by
pressing Enter, so a site can go from clone to fully working — with clearly-fake placeholder
contact details and colours — before you've heard back from the client with their actual phone
number or logged into their brand guidelines. Swap placeholders for real details whenever they
arrive (`wp option update client_phone "..."` — see below — or re-run the relevant part of the
wizard). This is also why it's safe to run the whole script non-interactively (e.g. piping
answers in from another script): nothing hangs waiting on input that isn't there.

Here's what an answered run looks like:

```
==> First-time setup — a few questions to brand this site for your client.
==> Every question has a bracketed default — press Enter to use it. None of
==> this needs to be final: if you don't have the client's real details yet,
==> use the placeholder and swap it in later (edit the file, or:
==> wp option update client_phone "...", client_email, client_address).
Client / site name [Client Site]: Acme Roofing Co
Tagline (optional): Roofing done right
Business email [hello@example.com]: info@example.test
Business phone [+44 (0) 0000 000000]: 020 7946 0958
Business address [123 Placeholder Street, London]: 42 Baker Street, London, NW1 6XE
Primary brand colour, hex [#2563eb]: #0f766e
Accent colour, hex [#f97316]: #f59e0b
==> One more colour is required (3 minimum total) so there's enough variety for section theming — see README.
Additional named colour (at least one required): Campaign green
Hex value for Campaign green: #198754
Additional named colour (blank to finish):
Heading font, Google Fonts family name [Poppins]: Playfair Display
Body font, Google Fonts family name [Inter]: Work Sans
==> Generating Tailwind colour tokens and updating theme.css...
Generated 3 colour palette(s): brand, accent, campaign-green
Section themes (name/alias): brand/alpha, accent/bravo, campaign-green/charlie
```

**Three colours minimum, always** — `brand` and `accent` alone don't leave enough variety for the
[section-theming system](section-theming.md) to be worth anything, so the wizard won't let you
finish the colour loop until at least one extra is given, and the generator itself refuses fewer
than three regardless of how it's invoked (`bin/generate-theme-tokens.mjs`'s own
`MINIMUM_COLORS` check, not just wizard UX).

The business email/phone/address become the `client_email`/`client_phone`/`client_address`
WordPress options, read by `sections/footer.blade.php` and `template-contact.blade.php`. Each
line renders **only when its option is non-empty**: there is no placeholder fallback in the theme
code, so clearing an option (or a site that never ran the wizard) shows nothing instead of
publishing dummy contact details. The wizard's bracketed defaults are real option values, so a
freshly bootstrapped demo site still shows them until you replace them. Enter `-` at the email, phone or
address prompt when the client has none: that option is left unset (deleted on a re-run), so nothing is
rendered for it, including the `mailto:` / `tel:` link.
If WooCommerce gets enabled in the same run, its own "Store address" prompt defaults to whatever
was just given here, rather than asking for the same address twice.

**Every named colour becomes a full 50–950 OKLCH scale**, generated by
`bin/generate-theme-tokens.mjs` (this directory's own `bin/`, i.e.
`web/app/themes/sage/bin/generate-theme-tokens.mjs`). `brand` and `accent` are always present;
the wizard accepts any number of additional named colours. The generator normalises names into
safe Tailwind slugs (for example, "Campaign Green" becomes `campaign-green`) and writes a
committed palette source at `config/brand-palette.json` (repo root).

**Two more colours always get added automatically beyond whatever the wizard asked for: a near-black
and a near-white**, `#000000`/`#ffffff` by default — every theme needs a dependable text/card
colour to fall back on, and hand-picking "should this specific brand colour use black or white
text" doesn't scale past a handful of themes. Each palette colour also carries a `role` field
(`brand`/`accent`/`black`/`white`) and a `styles` object — see the "Section theme roles and styles"
section below for the full shape and how to hand-tune either. The wizard asks, optionally, for the
client's own near-black and near-white hex (blank keeps pure `#000000`/`#ffffff`).

**Exact source hexes.** The scales are OKLCH and the 600 step is clamped for light colours, so a
client's exact brand hex may not appear on a scale. Every colour therefore also gets
`--color-{name}-exact` (the untouched hex; `bg-gold-exact`, `text-gold-exact`, and `brand-exact` /
`accent-exact` aliases) for the one place something must match their artwork precisely.

**Greys follow the brand.** The views and blocks use Tailwind's `neutral-*` greys for text, borders and
quiet surfaces. The generator redefines that whole scale (`--color-neutral-50` to `-950`) at Tailwind's own
lightnesses with a faint tint of the brand hue (chroma is 12% of the brand's, capped at 0.02), so a
rebranded site's 404, search form, author pages, breadcrumbs and every other `neutral-*` use follow its brand
without any view being edited. A pure grey brand stays pure grey.

**A light brand colour can fail as text.** The exact hex is for artwork, fills and large display type; it
is not automatically legible as body text on the light surface. A gold `#b08d4f` on a warm white
`#faf7f0` measures 2.9:1 (its generated `brand-600` 3.5:1), under WCAG AA's 4.5:1. For text on a light
surface use a darker step of the same hue: `text-brand-700` measures 6.6:1 and `text-brand-800` 10:1 there.
Check any new text/background pair rather than assuming; `wcagContrast` from `culori` is already in the
theme's `node_modules`.

**Logo and header theme.** The header shows the logo uploaded under Appearance > Customize > Site Identity (the
theme declares `custom-logo` support; the image is scaled by height, and WordPress gives it the site name as its alt
text) and falls back to the site name as text. It is a light header by default. To give it a dark or tinted one, name
a palette colour in `config/brand-palette.json`:

```json
"header": { "theme": "black" }
```

The header then wears that colour's own section theme (`.pkde-section` plus `.theme-black`, the same generated tokens
every Hero and CTA uses): its background, text, hover (the theme's highlight) and border, in the desktop bar and the
mobile menu. Unset, the header is exactly as before. `npm run theme:generate` validates the name, and **checks the
contrast**: the theme's text and its highlight must each measure at least 4.5:1 on its background, resolved from that
colour's `styles`, or generation stops with the measured numbers (fix that colour's `styles` or choose another colour).
There is one logo; a second "light logo" for a site that needs both a light and a dark header is not built yet.

**Header styling hooks.** The header's logo height and nav typography are CSS custom properties declared in `app.css`
(`:root`), with defaults equal to the plain look, so a site restyles them in its own CSS without editing the template:

| Variable | Default | Controls |
|---|---|---|
| `--header-logo-h` / `--header-logo-h-sm` | `2rem` / `2.5rem` | logo height below / from the `sm` breakpoint |
| `--nav-weight` | `500` | nav link font weight (desktop bar and mobile menu) |
| `--nav-transform` | `none` | e.g. `uppercase` |
| `--nav-tracking` | `normal` | nav letter spacing |

```css
:root { --header-logo-h: 2.5rem; --header-logo-h-sm: 3rem; --nav-weight: 600; --nav-transform: uppercase; }
```

The logo's link is `display: flex`, so the image's baseline leaves no gap under it.

The logo carries a `sizes` attribute matching the width it is actually drawn at (its height is fixed by the variables
above, so the width follows from the image's aspect ratio), e.g. a 240x64 logo gets `(min-width: 640px) 150px, 120px`.
The browser then picks a small `srcset` candidate instead of the full-size file. The calculation assumes the default
heights (32px below `sm`, 40px from `sm`); if a site overrides `--header-logo-h` / `--header-logo-h-sm`, tell it the new
pixel heights: `add_filter('pkde_header_logo_heights', fn () => [40, 48]);`.

**A themed header is opaque.** The default header is the translucent white bar with a backdrop blur; a header with
`header.theme` is the section theme's solid background (so a dark bar never shows page content through it).

**A header colour of its own.** `header.theme` borrows a palette colour's section styles, and every `.theme-{name}`
block (Hero, CTA, cards) uses the same ones. To get a bar that matches nothing else, for example a deep navy, **add
a colour to the palette** and point the header at it, rather than editing `brand`'s or another colour's `styles`:

```json
"colors": [ ..., { "name": "navy", "hex": "#0b2545" } ],
"header": { "theme": "navy" }
```

Regenerate: the new colour gets its own backfilled styles (and a `.theme-navy` section theme, which other blocks may
also use), the contrast check runs on it, and `.theme-brand` is untouched (checked: its CSS is byte-identical
before and after).

**A deep colour needs its exact hex as the background.** When a colour's `styles` are backfilled, `background` is its
600 step, and the 600 step is clamped to a lightness of at least 0.47 so a saturated brand colour stays legible. A
deliberately deep hex such as `#002457` (lightness 0.27) would therefore render as a mid navy bar. To get exactly the
hex you chose, set that colour's `styles.background` to its exact-hex token, `NAME-exact` (the same `--color-NAME-exact`
described above), once, in `config/brand-palette.json`, then regenerate:

```json
{ "name": "navy", "hex": "#002457", "styles": { "background": "navy-exact", ... } }
```

(`styles` are computed once and then left alone, so run the generator first to backfill the rest, then change
`background`.) The header contrast check understands `NAME-exact` and measures the text against the true hex, so a pair
that fails still stops generation. Checked with `#002457`: `.theme-navy` gets `--pkde-theme-background:
var(--color-navy-exact)`, and a deliberately unreadable content colour (`navy-800`) failed at 1.38:1.

**Highlights are contrast-checked.** When a colour's `styles` are first backfilled, its `highlight`
is the step of its hue nearest the intended one (200 on a dark section, 600 on white) that measures at
least 4.5:1 against the section background (best available if none does). The old fixed picks
measured 2.6:1 and 3.5:1 on mid and cream colours. Existing `styles` are never recomputed.

**"Role" decouples what a colour is *called* from what part it *plays*.** A colour literally named
`brand`/`accent`/`black`/`white` gets that role automatically — every existing palette (including
this template's own default) already names its colours that way, so nothing has to change to keep
working. But a client's real brand colour doesn't have to be named `brand` at all: give it
`"role": "brand"` explicitly and call it whatever the client actually calls it (`"name": "ocean"`)
— `--color-action`, `--color-highlight`, and every already-hardcoded `bg-brand-600`-style class in
the theme's own Blade partials keep resolving correctly regardless, since the generator emits an
alias scale under the role name whenever it differs from the colour's own. Exactly one colour may
hold each role — the generator fails loudly (not silently) if two ever claim the same one.

**Every colour's `styles` (background/content/highlight/button colours/border/`card`) is computed
once, then never touched again.** The first time a colour is seen without a `styles` object, the
generator fills one in — including picking `content` (and the button/card colours that need to
match it) by *measured* WCAG contrast against whichever colour holds role `black` and role `white`,
not by assuming white always works. That's a real fix, not just a nicety: this template's own
default `accent` (`#f59e0b`, an amber) measures 2.15:1 contrast for white text at its own
generated 600 step — well under WCAG AA's 4.5:1 for normal text — against 9.78:1 for black.
Whatever the generator picks is written into `config/brand-palette.json` as plain data (e.g.
`"content": "black-950"`) and stays exactly as written on every future run, however you edit it —
see "Section theme roles and styles" below for the full shape and the `card` pointer specifically.

It generates/updates six files:

- **`config/brand-palette.json`** (repo root) — the human-editable palette and font source of
  truth.
- **`resources/css/generated/brand-tokens.css`** — generated Tailwind `@theme` colour variables
  and `@source inline()` utility generation. It provides utilities such as `bg-brand-600`,
  `text-campaign-green-700`, and `border-accent-300`, and makes the colours available to the
  WordPress editor via `wordpressThemeJson()`.
- **`resources/css/generated/section-themes.css`** — one re-themeable "section" per colour,
  `.theme-{name}`/`.theme-{alias}` — see [Section theming](section-theming.md).
- **`resources/css/generated/card-themes.css`** — two opt-in card recolour variants per colour,
  `.theme-{name} .pkde-card-tinted`/`.pkde-card-bold` — see
  [`resources/blocks/README.md`](../resources/blocks/README.md)'s "Post/product cards can also go
  beyond plain white" and "Section theme roles and styles" below for the full rationale. Tinted is
  always the same colour as its own section, a shade lighter; Bold borrows whichever colour the
  section's own `styles.card` points at (see below) wholesale.
- **`resources/js/generated/theme-options.js`** and **`resources/generated/theme-options.php`** —
  the same `{value, label}` list (client-facing names like "Campaign Green", not raw slugs), once
  for any themed block's `edit.jsx` (`THEME_OPTIONS`, imported by `hero/edit.jsx`, `cta/edit.jsx`,
  and `hero-slide/edit.jsx`) and once for PHP (`bin/generate-demo-content.php`'s per-colour
  Hero/CTA/Hero Slide demo sections). Before these existed, each themed block's editor UI
  hardcoded its own `THEME_OPTIONS` array — correct only by coincidence for whatever colour count
  the block happened to be written against, silently capped (6 generic `alpha`–`foxtrot` entries)
  the moment a real palette had more colours than that. Any new block that adds a `theme` select
  should import from `theme-options.js` rather than writing its own list, for the same reason.

`npm run theme:check` (from this theme's own root) verifies all five generated files (the three CSS
files plus the two theme-options files) are actually in sync with `config/brand-palette.json` —
useful in CI or before a commit, since nothing else catches a hand-edited generated file or a
config change nobody regenerated for.

## Section theme roles and styles

Each colour in `config/brand-palette.json` looks like this once the generator has run at least
once (`role` only appears when applicable; every colour gets a `styles` object):

```json
{
  "name": "accent",
  "hex": "#f59e0b",
  "role": "accent",
  "styles": {
    "background": "accent-600",
    "content": "black-950",
    "highlight": "accent-200",
    "buttonPrimaryBackground": "black-950",
    "buttonPrimaryText": "accent-600",
    "buttonSecondaryBackground": "transparent",
    "buttonSecondaryText": "black-950",
    "border": "accent-500",
    "card": "black"
  }
}
```

Every `styles` value except `buttonSecondaryBackground` (always the literal keyword `transparent`)
and `card` is a plain `{colourName}-{step}` reference to an already-generated Tailwind token (e.g.
`"black-950"` → `--color-black-950`) — there's no separate value vocabulary to learn beyond what
`brand-tokens.css` already produces. `card` is the one pointer field: a bare colour *name* (no
step), naming another entry in `colors[]` whose *entire* `styles` object gets borrowed, one hop,
for this colour's `.pkde-card-bold` variant (`buildCardThemesCss()`) — it never chases whatever
that colour's own `card` might in turn point to.

**Computed once, left alone forever after.** The generator only ever fills in a `styles` object for
a colour that doesn't have one yet — an existing one, however it got there (auto-computed last run,
or hand-edited just now), is never recomputed or overwritten. Want a different pairing? Edit the
field directly and rerun:

```bash
# Give coral's cards Slate's colours instead of the auto-picked black/white:
# "card": "black"  →  "card": "slate"   (config/brand-palette.json)
docker compose exec -T node node bin/generate-theme-tokens.mjs
```

Only what you touched changes — every other colour's `styles` stays exactly as it was.

**To re-brand later, or do it by hand:**

```bash
docker compose exec -T node node bin/generate-theme-tokens.mjs \
  --color brand=#0f766e \
  --color accent=#f59e0b \
  --color "Campaign Green=#198754" \
  --display-font "Playfair Display" \
  --sans-font "Work Sans"
```
(Run from `web/app/themes/sage`; this is the same generator `bin/setup` calls.)

Edit `config/brand-palette.json` and rerun `node bin/generate-theme-tokens.mjs` when you want to
hand-tune the input palette. Do not edit `generated/brand-tokens.css` directly.

One thing worth understanding if you add colours to the palette: Tailwind only generates a
utility class (and therefore only exposes a colour in the block editor) once it's actually
referenced somewhere scanned by `@source`. The generator writes `@source inline(...)` entries
for every configured colour and scale, so no manual safelist maintenance is needed.

## Fonts: self-hosted, preloaded, and optionally your own files

Unlike colours, fonts aren't generated by `bin/generate-theme-tokens.mjs` at all — it only
validates `config/brand-palette.json`'s `fonts` object (`validateFonts()`) and writes it back
unchanged. The actual work — self-hosting, real `<link rel=preload>` tags, variable-font detection,
and CLS-safe metric-matched fallback fonts — is done by **`web/app/themes/sage/vite.config.js`'s
own `fonts:` option**, using `laravel-vite-plugin`'s official Fonts feature
(`laravel-vite-plugin/fonts`), rendered into `<head>` by the `@fonts` Blade directive in
`layouts/app.blade.php`. There is no third-party request to `fonts.googleapis.com`/
`fonts.gstatic.com` at all — every font file is fetched once at build/dev-server time and served
from this theme's own build output from then on.

**The common case — a Google Fonts family name — needs no change from before:**

```json
"fonts": {
  "display": "Poppins",
  "sans": "Inter",
  "mono": "IBM Plex Mono"
}
```

`mono` is optional. Each slot's `alias` is always fixed to the slot name (`display`/`sans`/`mono`),
so the resulting CSS variable is `--font-display`/`--font-sans`/`--font-mono` — exactly what every
existing `font-display`/`font-sans`/`font-mono` Tailwind utility class already expects sitewide
(`theme.css`'s own `@theme` block declares the same three names as generic fallbacks, for when
Tailwind needs *some* value at build time — see that block's own comment). Nothing else needs
touching when you change a font name; regenerate as usual and `vite.config.js` picks the new value
up on its own next read of `config/brand-palette.json` (no restart needed in dev, since Vite
reloads its own config on change; a full `npm run dev`/`build` picks it up either way).

**A family with a real variable-weight font gets one self-hosted file covering every weight you
use; a family that only ships static per-weight files gets one file per weight** — confirmed
directly: this template's own default `sans` (Inter, genuinely variable on Google's catalogue)
builds to a single `inter-variable-*.woff2` regardless of how many weights are used on the page,
while `display` (Poppins, static-only on Google's catalogue — not every popular family has a
variable version) builds to one file per requested weight. Neither generator nor this doc can make
a family variable that isn't; the plugin picks whichever is actually true of the real font files.

**To load fewer weights from Google Fonts** (every static-only family downloads one file per weight,
and a plain string requests 400, 500, 600 and 700), use the object form with `"source": "google"`
and a `weights` list:

```json
"fonts": {
  "display": { "source": "google", "family": "Montserrat", "weights": [500, 600, 700] },
  "sans": "Inter"
}
```

`weights` replaces the default list for that slot (`vite.config.js`'s `DEFAULT_GOOGLE_WEIGHTS`);
`styles`, `subsets` and the other options listed below work the same way. Only request weights the
design actually uses: a Tailwind class for a weight you did not load (`font-bold` with no 700) is
synthesised by the browser or falls to the nearest loaded weight.

**To use your own font files instead of a Google Fonts name**, set an object with
`"source": "local"` instead of a plain string:

```json
"fonts": {
  "display": "Poppins",
  "sans": "Inter",
  "mono": {
    "source": "local",
    "family": "Acme Mono",
    "src": "resources/fonts/source/acme-mono/*.woff2"
  }
}
```

`src` is a path or glob **relative to this theme's own root** (i.e. `web/app/themes/sage/`, where
`vite.config.js` itself lives) — put the raw files somewhere under `resources/fonts/source/` (a
plain, project-specific location; nothing else reads from it) and point `src` at them. Weight and
style are inferred from each filename when possible (`AcmeMono-Bold.woff2` → weight 700); for exact
control instead of inference, use `variants` in place of `src`:

```json
"mono": {
  "source": "local",
  "family": "Acme Mono",
  "variants": [
    { "src": "resources/fonts/source/acme-mono/AcmeMono-Variable.woff2" }
  ]
}
```

A single variable font file (one `src` entry, no `weight` given) is treated the same as a
Google-sourced variable font — one self-hosted file covering its whole weight range. See
`node_modules/laravel-vite-plugin/dist/fonts/types.d.ts`'s `LocalFontOptions`/`LocalVariantDefinition`
for every supported field (both `source: "google"` and `source: "local"` objects also accept
`weights`/`styles`/`subsets`/`preload`/`fallbacks`/`optimizedFallbacks` — passed straight through to
the plugin; `vite.config.js`'s own `buildFontDefinitions()` only fills in defaults, it doesn't
restrict what you can set).

**A real, confirmed dev-server-only bug, and why `vite.config.js` carries its own fix for it:**
`laravel-vite-plugin`'s Fonts feature 404s every font in `npm run dev` specifically on a project
with a non-default Vite `base` — which this theme always has, since Vite runs from inside a
WordPress theme directory rather than a Laravel app root. Traced directly: the font dev-server
middleware only ever answers requests at the literal unprefixed path
`/__laravel_vite_plugin__/fonts/*`, but the URLs it hands to the browser are built from the `hot`
file's own content, which already has `base` baked in (correctly, for every *other* dev asset) — so
every font request 404s with the prefix doubled in. Production builds are unaffected (they resolve
fonts from `public/build/fonts-manifest.json`, a completely different code path) — this is purely a
`npm run dev` problem. `vite.config.js`'s own `fontDevServerBasePathFix()` plugin strips that prefix
back off before `laravel-vite-plugin`'s middleware ever sees the request; see that function's own
comment for the exact mechanism, including why it has to register its middleware eagerly rather
than as Vite's more common post-hook style.
