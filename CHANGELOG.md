## 2026.11.20.4

The site-wide CTA band (`sage/cta-band`) is full width in the editor canvas, as it is on the page (TPL-246, an owner bug). **Adopt:** bump the kit on any site that uses the band (bb); nothing else. Proved on the template stack in real Chrome with a page that carries the band and no `align` in its markup, as bb's does: **before** the band was 768 px wide in the canvas (the content width) while the page printed it 1440 px wide; **after** it is `alignfull` and 1160 px, the full canvas, with the paragraphs around it still 768 px, and the page is unchanged.

- **The cause.** The page's render already prints `alignfull`, but the block declared `align: ["full"]` support with no default, so a band saved without `"align":"full"` (every existing one) got no `alignfull` class in the editor, and the canvas gave it the content width. The block now has the attribute `align` with the default `full` (as the Section block has); WordPress leaves a default out of the saved comment, so no saved page changes.

## 2026.11.20.3

Product gallery: no more tall flash before it settles (TPL-244, an owner bug on bb's product page; a follow-up to TPL-181 and TPL-190). **Adopt:** bump the kit on any shop (bb, tcs, js and every site with WooCommerce); a hotfix candidate for staging. Measured on the real dev product pages (read-only, the new rules injected in memory, Chrome, CPU 4x slower, 1.6 Mbit/s); NOT on a server.

- **The cause.** WooCommerce's script builds the slider's viewport first and sets its inline height about 100 ms later. In between, the viewport has no height of its own (the kit keeps `height: auto`), and the slides, still four times too wide, stack: bb's gallery was 14,300 px tall on a desktop and 8,200 px on a phone for one frame, which made the page below jump twice. Layout shift on bb: **0.247 (1440) and 0.673 (390)**; on tcs 0.048 and 0.521.
- **The fix.** Until the inline height is there (`.flex-viewport:not([style*="height"])`) the viewport has the ratio of the picture the kit shows, **4:3**, or the site's `--pkde-gallery-ratio`; once the script has set its height the viewport follows the content again, so a gallery that shows its pictures at another ratio is never clipped. The gallery pictures take the same `--pkde-gallery-ratio` (4:3 by default, as before), so a site that sets it gets pictures and viewport at one ratio.
- **Result.** bb: layout shift **0 on a desktop (median of 3; one run 0.007) and 0 on a phone**, the viewport 447 px from the first frame. tcs (square photos): the flash is gone (0.048 to 0.019 and 0.521 to 0.073) and the photos are not clipped (viewport 620 px, picture 618 px); **a site that shows its pictures at another ratio sets `--pkde-gallery-ratio` to it** (tcs: `1`) and measures 0.0001 and 0.
- Pest 187.

### The page title follows the theme's H1 (A, TPL-200)

The page title follows the theme's H1 (WP-99 A, TPL-200; owner 2026-11-19). **Adopt:** bump, then look at the title band once on staging. **tcs:** its page titles become the size of its content H1 (69 px on a desktop instead of 48 px) and the colour of its other text. **bb and any theme with no H1 style:** unchanged.

- **The H1 of the title band** (`partials/page-header`) loses its Tailwind size classes. When the theme defines an H1 style (`theme.json` `styles.elements.h1` with a font size, or the same set in the Site Editor) the H1 takes family, size, weight, line height, letter spacing and colour from it, exactly like an H1 in the content, and the `--pkde-page-header-title-*` variables do nothing. When the theme defines none, `App\page_title_follows_theme()` is false and the H1 keeps the kit's title look (class `pkde-page-title--kit`, the same variables as before): **this is a deliberate departure from the brief's wording, and it is needed:** bb's theme.json has no H1 style (its large headings come from block settings), so an unconditional "follow the theme" would have made bb's page titles 16 px body text. Filter `pkde_kit/page_title_follows_theme` overrides the decision. A size set in the block editor on a heading still wins (the kit has no rule on block-content headings; one Pest test says so).
- **No `--pkde-page-title-size` variable:** a variable that is unset by default cannot fall through to the theme's size in CSS (an unset `var()` makes the property invalid, and WordPress's own rule is not a fallback); a site that wants the band's title smaller writes `.page-header h1 { font-size: ... }` in its own CSS, which beats WordPress's `:root :where(h1)`. In kit-look mode the existing `--pkde-page-header-title-size` works as before.
- **Measured in real Chrome on tcs's and bb's dev pages (read-only; the new rules emulated in memory by rewriting the fetched stylesheet):** tcs, blog, shop, a category and contact, at 1440 and 390: before 48 px / 36 px, weight 200, a near-black title; after 69.12 px / 36.8 px, line height 72.6 / 38.6 px, spacing -0.83 / -0.44 px, colour rgb(53, 59, 61): **identical to a bare H1 in its content in all 8 views** (size, weight, line height, spacing, colour, family). bb, blog, shop and contact at both widths: 48 px / 36 px, Addington, weight 400, unchanged to the pixel (the H1's box is 60 / 45 px high before and after). bb's category view was not measured (no category link was found on its shop page); tcs's is among the 8. Not seen: the title with an editor-set size in a real page.
- Pest 155 (the follow / not-follow render, the no-block-heading-rule check). The contrast check in `generate-theme-tokens.mjs` still assumes the kit's ink on the band; a theme that follows its own H1 colour checks that colour itself.

## 2026.11.19.4

Shop filters v2: correct counts, a request check before any product query, filters a shop declares (WP-96, TPL-192; owner decision: no Filter Everything). **Adopt:** the shops (tcs, bb, js, el) bump, add `config/shop-filters.php` declaring the groups they show now (without the file nothing visible changes except that the counts are right), and check five combinations on staging. - **The counts are right.** On the template stack with WooCommerce and a fixed catalogue, a matrix of 28 combinations compares the number beside every option with the grid total after choosing that option alone in its group: **before 153 options were wrong in 28 of 28 combinations** (attribute, brand and category counts too high when a price range, the sale/new/featured views, a search or hide-out-of-stock was in play, because the counts ignored them; a parent category too low because its children were not counted: Furniture showed 1 where the grid shows 11), **after 0**. Known limits: variation-level stock; a search plugin such as Relevanssi (not proved); WooCommerce 9.9 or later (its price clause).
- **Declared per shop** (`config/shop-filters.php` in the theme, Acorn config, defaults merged by `KitServiceProvider`; escape hatch `pkde_kit/shop_filters`; labels through `pkde_kit/shop_filter_label`): groups in order with `source` (a product taxonomy, `price`, `stock`), `label`, `hierarchical`, `order` (`name`, `menu_order`, `count`), `limit`; `hide_empty_terms`, `max_values_per_group` (10), `max_active_groups` (6), `counts_cache_ttl` (3600). - **Load.** A request with `sage_filter_*` arguments is checked in `pre_get_posts` before any product query: more than the caps, or only unknown values, is a **404 with no product query and no filter UI**; valid but not canonical (values unsorted or repeated, empty values, a dropped unknown value, a bad price) is a **301 to the one canonical URL**. A malformed argument (`sage_filter_x[a][b]=1`) used to answer 500; it no longer does. The counts need at most `2 x (active groups) + 2` product-side queries on a cache miss and none on a hit (they are cached, keyed by the canonical choices, the archive and a catalogue version that moves when a product, its stock or a product term changes). On the template stack with 1,270 products the page time barely moves (the rest of the page dominates: about 90 to 130 ms either way); the gain is the bounded work under a flood: of 500 scripted random combinations the old kit rendered 495 in full, the new one answers **75 percent (374) by a 301 or 404 and renders 25 percent**.
